# 闪卡及服务器奖励：AI、DIY、原版线旧客户端兼容性复核

审查日期：2026-09-20。复核目标是各条线玩家继续使用原来的客户端，连接升级后的原服务器；新闪卡包与新普通包来自同一套客户端源码。不是要求旧正式服客户端跨服连接 DIY，也不是维护两个客户端代码分支。

**结论：不强制普通玩家升级客户端，在已检查的协议和数据结构上可行，并已有运行证据支持。当前本地实现仍不满足上线条件，必须修复服务器故障隔离、旧请求保存语义和数据库回滚问题。没有发现必须依赖客户端升级才能解决的闪卡协议障碍。**

这份报告补充此前 `LegacyClientCompatibility-20260920.md`。此前“不放行当前实现”的结论仍成立；不能把这些实现缺陷解释成“旧客户端天然无法兼容”。本次没有修改产品代码、合并、提交、推送或部署，也没有访问实际玩家数据库。

## 2. 已经验证的兼容依据

### 2.1 卡牌身份没有因闪卡改变

当前 `Common/Models/CardStatus.cs:43-45` 仍以原 `CardId` 表示卡牌，新增的是 `bool? IsPremium`。卡组继续使用 `List<string> Deck`，用附加 `Dictionary<string,int> PremiumCards` 表示闪卡副本数量、`bool? PremiumLeader` 表示领袖外观。

因此同一张牌普通版与闪卡版的规则身份相同。旧客户端忽略额外属性后仍使用原卡图与卡牌数据。不能以后再给闪卡另造 CardId，或改变旧属性类型、旧指令编号、参数顺序；“追加 JSON 属性”也不等于任意增加操作参数都安全。

本轮独立协议探针分别使用：

- AI、DIY：从各自固定提交重新构建的完整旧 Common；各自仓库内 SignalR Client/Core、Http.Connections.Client、Protocols.Json DLL；原 `AOThelper` converter。
- master：仓库内旧 `Cynthia.Card.Common.dll`、旧 SignalR DLL 和 `Newtonsoft.Json.dll`，未用当前 Common 替代。
- 三个探针均运行于桌面 .NET 5.0.7。AI/DIY 的部分支持程序集和 System.Text.Json 来自该运行时；不是完整 Unity/IL2CPP 环境。

**每条线 8 条行为检查 + 1 条程序集记录，三条线全部通过。** 检查包括旧类型确实没有 IsPremium、解析新服务器实际构造的闪卡 CardStatus、嵌套领袖/手牌/场地解析、重复原卡 ID 保留、旧卡组保存省略未知字段、旧操作帧解析与内层 JSON 解析、旧 RPC 完成响应解析。这里“旧保存省略未知字段”通过，只证明旧客户端行为，服务器仍须正确处理缺失字段。

实际加载的核心协议 DLL 与对应快照 SHA-256 一致。AI/DIY 版本 `5.0.821.31805`；master 版本 `3.0.0.19227`，其 Newtonsoft 为 `12.0.2.23222`。这不是只拿新客户端模拟“关闭闪卡”。

### 2.2 不调用新接口，也能完成真实服务器对局并拿到奖励

另建了两个没有 IsPremium/PremiumCards 等新模型的旧 AI 协议客户端，连接当前本地产品服务器。客户端使用上游旧 Common、旧 SignalR 和 converter；用上游 AIPlayer/RandomAutoAIPlayer 作为无界面的选择驱动，经正常 Hub 加入两个不同账号的玩家房间。服务器看到的是两个 ClientPlayer，非内置 AI 房间。

隔离数据库给第一个合成账号预置合法闪卡拥有权和卡组选择，只用于制造有闪卡标记的牌局。客户端只调用：`Register`、`Login`、`MatchOfPassword`、`GameOperation`、`GetUserCount`。没有调用 GetDailyQuests、GetPremiumCollection 或合成接口，也没有订阅 DailyQuestsChanged。

结果：

| 项目 | 实测 |
| --- | --- |
| 正常完成两小局、收到 GameEnd | 双方成功，第一位胜、第二位负 |
| 收到的对局操作数量 | 233 / 223 |
| 含 `IsPremium:true` 的操作数量 | 45 / 26；双方旧模型均能继续处理 |
| 胜者服务器余额 | 5045 = 初始 5000 + 登录 20 + 两皇冠奖励 25 |
| 胜者每日记录 | Crowns=2，PowderGranted=45 |
| 另一方服务器余额 | 5020，Crowns=0 |
| 对局后旧 RPC | 双方继续成功 |

服务端奖金额和进度由测试主机直接读独立 Mongo 数据验证，未通过新客户端接口触发补领。因此“登录和对局奖励必须依赖新版客户端”的说法不成立。现有服务器已经有主要的权威触发点：`GwentServerService.cs:420`、`GwentMatchs.cs:37`、`GwentServerGame.cs:243`。

这是**一场完整的无界面旧协议对局**，不是发布旧 Unity 包的画面、输入、Android IL2CPP 验收，也不是已经移植到 .NET 10 AI 服务器的结果。先前的旧库真实 WebSocket 9 条记录也通过，包括注册、登录、保存、匹配取消、多语言往返和忽略新通知；那组构造帧测试与本轮完整对局分开记录。

### 2.3 旧方法签名可保留

三个目标 Hub 与本地的源码签名对照，未发现旧公开方法被删除或参数改变；Register 从 CLR bool 变 Task<bool>，线上返回仍为 bool，旧库真实调用通过。新增奖励/合成/语言接口是增量，旧客户端没有必须调用它们的理由。行为兼容还取决于下述服务器内部依赖。

## 3. 当前代码必须先修复的四个问题

下列问题已在前一轮隔离测试复现；本轮没有修补产品代码，所以仍存在。完整结果见旧报告及 `work/CompatibilityAudit/20260920/compatibility-results.json`：32 条记录，23 通过、9 失败；部分通过记录用于证明故障注入条件成立。

### A. 普通游戏路径强依赖闪卡钱包

- `GwentServerService.cs:420`：登录态发布前等待每日奖励。
- 同文件 `:520`、`:736`、`:794`：匹配、新增卡组、修改卡组等待钱包读取。
- `GwentDatabaseService.cs:315-316`：账号写入后等待初始粉尘；后者失败时注册报错，但账号已占用。

仅制造钱包反序列化异常或奖励写入失败，普通用户集合仍健康时，旧登录、配卡和匹配会失败。与旧客户端能否识别字段无关，新客户端也不能消除此风险。

**修改方向：**普通账号认证、合法卡组操作和对局不以奖励/外观子系统成功为条件。外观暂不可读时使用普通外观继续游戏，同时保留原来的持久化选择；合成或修改拥有权安全失败。不能因降级把玩家存档改成空外观或伪造拥有权。注册的可选赠送失败不能伪装成账号创建失败。

### B. 小局结算等待奖励，慢请求会拖住双方

`GwentServerGame.cs:197-243` 的三次重试仍直接 await 奖励任务；慢任务没有应用层时间边界。故障注入使奖励未完成时，小局推进停住；释放任务后恢复。

**修改方向：**把奖励处理从小局推进的等待链移出，并提供稳定 match/round 键、持久补偿与幂等重试。仅 fire-and-forget 会在进程退出后丢奖，不能算完成。数据库全面不可用与只有可选钱包失败要分开验收，不能许诺在核心数据都不可读时仍正常游戏。

### C. 旧客户端保存卡组会重置外观意图

旧客户端正确地省略不认识的 PremiumCards/PremiumLeader；当前 `CardInventory.InitializeDeck` 却将 null 按拥有权重新初始化。例如玩家用新客户端明确选了全普通卡，随后用旧客户端改名，服务器可能重新给他选择已拥有的闪卡。

**修改方向：**已有卡组请求里缺少外观字段表示“保留现有选择”；显式空字典/false 表示“主动取消”。根据新的原卡 ID/张数裁剪超出的选择；新增旧格式卡组默认普通外观。不要把“旧客户端不会发送”当作用户主动修改外观。

### D. JSON 兼容不代表原数据库可直接回滚

当前 PremiumCards/PremiumLeader 跟随 UserInfo.Decks 写进旧 user 文档。新文档交给上游旧 AI 的 DeckModel，以 AI 使用的 MongoDB.Driver 3.9.0 读取，出现 `Element 'PremiumCards' does not match any field or property`。这是**旧服务器 BSON 读模型**问题，不是旧客户端 JSON 问题。

**修改方向：**优先让粉尘、拥有权、奖励、卡组外观继续存独立集合，以账户 ID + 稳定 DeckId 关联；原 user.Decks 保留其原结构。网络 DTO 可以组合发送新字段，数据库 DTO 不必跟着扩展。若保留嵌套新字段，必须有经过演练的兼容迁移和回滚方案，不能只靠忽略未知字段，因为旧服务整文档 ReplaceOne 还可能丢掉新状态。

## 4. 三条线的移植差异

| 目标 | 当前证据 | 必须保留的边界 |
| --- | --- | --- |
| AI | 旧模型/旧库解析通过；对本地新服务器的完整旧协议对局通过 | AI 的 .NET 10、Mongo 3.9、AsciiSafeJsonHubProtocol、专用地址/端口、卡池和部署配置；还需构建实际 AI 候选服务器 |
| DIY | 固定上游旧模型/旧库解析通过 | 最新 DIY 有 `SetEnemyDeck=43`、`SetNameInfo=44`；不能被本地或 AI 的枚举覆盖 |
| 原版 master | 仓库旧 Common/旧库解析通过 | 原卡池、原素材、原服务器地址、数据库 `gwent`；先核对实际正式服发布版本，再做目标服务器移植 |

AI、本地和 master 为 `SetNameInfo=43`；最新 DIY 为 `SetNameInfo=44`。其他对应旧项在此次比较中相同。DIY 的 43 用于 SetEnemyDeck，盲目合并可能把名称数据当牌库数据处理。这是跨分支协议差异，不能当作闪卡必需的版本升级，也不能只看 Hub 方法名就宣布兼容。

原版数据库逻辑名为 `gwent`，本地与 AI/DIY 为 `gwentdiy`，服务器内部类型/API 也有年代差异。移植应在目标线保留既有账号与游戏规则，不能直接覆盖数据库访问类或整个 Common/card map。各服本来就存在的业务差异与“维护两个闪卡客户端代码版本”是不同问题；不需要为了支持旧包复制一套新客户端实现。

本地与 AI 已有 20 个文本冲突，且本地 DIY 历史还有非闪卡的最高 MMR 迁移。应按功能移植用户的改动，不能将整条分支当作纯外观补丁直接上线。

## 5. 仍未完成的上线证明

“旧客户端可以不升级”是本轮得到支持的架构目标；“任意旧包、所有玩法、任何故障都绝不受影响”尚无证据，不能签字承诺。

修复后至少需要：

1. 分别构建目标 AI/DIY/原版候选服务器，运行各自既有回归；不改变旧操作编号、参数和基础卡池。
2. 使用实际发给玩家的旧 Windows/Android 包，覆盖旧旧、旧新普通、旧新闪卡；出牌、领袖、复制/生成/变形、隐私、观战、掉线与重登、完整结算。新两包互打不能替代旧包验收。
3. 奖励/钱包异常和超时下仍完成普通注册、登录、配卡、匹配和对局；恢复后幂等补奖，旧卡组保存保持外观意图。
4. 匿名数据副本的升级 → 指定旧服务器回滚 → 再升级，确认原账号/卡组/战绩/饰品及新钱包/外观均保留。
5. 当前 20/25/35/45 奖励配置下的测试全部通过。既有矩阵仍有 61 条旧金额假设导致的失败；复制二进制换回历史配置得到 247/247 只用于定位测试过时，不是当前配置的绿色验收。
6. 全服一次性 5000 粉尘补发、奖励账本增长与对局共存的负载验证。ProcessedRoundIds 持久去重历史不能简单清空；应在不破坏跨日/重启幂等的前提下做容量设计。连续在线跨日是否算“每日登录”也应固定服务器规则，不能依赖新版任务面板轮询作为触发条件。

以上属于同一套服务端功能的兼容验收和几处有边界的修复，不需要立即引入两套长期客户端代码。当前证据支持继续沿“不强制普通玩家更新”实现，再用真实旧包作为回归样本。
